# Recursive derivation trees

`mosaic.verification.derivation` builds bounded trees by recursively expanding
every request that matches a registered decomposition rule.

Each node records its exact request, its structural path, and (when applicable)
the registered rule ID. The current chain-rule expander declares three
subrequests: the outer derivative, the inner derivative, and the final
composition identity. If the inner derivative is itself a supported
power-composition request, the builder expands it recursively.

## Completeness contract

`validate_derivation_tree(request, tree)` checks:

- the root is bound to the exact original request;
- every applicable registered rule is expanded (no silently omitted rule);
- each expanded node has exactly the subrequests generated by that rule;
- rule IDs, child order, paths, and leaf structure match the registered
  deterministic expansion;
- the recorded node count is accurate.

The builder and validator enforce configurable depth and node limits. A
request with no applicable rule is a valid leaf; this means only that the
current registry has no matching decomposer, not that the task is solved.

## Trust boundary

A valid tree establishes structural coverage relative to the current
allow-listed registry. It does not prove the rule mathematically sound, prove
the leaf obligations, or establish that the registry contains every useful
mathematical method. Tree validation is not a proof kernel. Any downstream
evaluation retains the statuses and limitations of its own checkers, and
must not promote `EXPERIMENTAL` to `PROVED`.

## Recursive execution

`mosaic.verification.recursive_execution.execute_recursive_derivation`
provides a bounded end-to-end action for this structure. It builds and
validates the complete tree, replays each registered rule's verifier and
deterministic executor at every internal node (including nested applications),
compiles the terminal requests into the dependency-aware obligation graph,
and creates strict request-bound candidate records for supported terminal
operations. The ordinary graph evaluator then checks those candidates in
dependency order and retains every rule precondition.

The convenience executor accepts the same `max_depth` and `max_nodes`
budgets as tree construction. Unsupported leaf operations fail closed. Its
result includes the tree, the path and ID of each executed rule, and the
complete obligation-graph result. It does not call external models or trust
model-generated code. A successful result remains `EXPERIMENTAL`; recursive
execution is not a formal proof and does not discharge unsupported domain
preconditions.
